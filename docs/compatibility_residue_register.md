# Compatibility-Residue Register

This register is the authoritative planning inventory for known active
compatibility surfaces identified through Campaigns 1-5. It documents ownership,
consumers, replay/provenance impact, verification status, and retirement
readiness. It does not retire compatibility or change behavior.

Use this register before changing aliases, legacy vocabulary, compatibility
adapters, temporary bridges, historical payload formats, import re-exports,
fallback compatibility, replay compatibility, serialization compatibility, API
compatibility, or test compatibility.

## Status Model

| Status | Meaning |
|---|---|
| Active | Required by current runtime, tests, docs, governance, or generated artifacts. Do not retire. |
| Transitional | Intended to shrink or retire after caller, replay, provenance, and governance evidence exists. |
| Awaiting Evidence | Current surface exists, but retirement state depends on fresh consumer or incidence evidence. |
| Retirement Candidate | Evidence suggests possible retirement, but no removal is approved by this register. |
| Permanent Compatibility | Compatibility is expected to remain as a supported public or historical read path. |

## Maintenance Rules

- Add or update a register row before changing compatibility behavior.
- Do not retire compatibility from this register alone; retirement requires a
  package with caller evidence, replay/provenance review, tests, and closeout.
- Keep compatibility rows tied to canonical owners. Compatibility surfaces do
  not become semantic owners.
- For import re-exports and compat barrels, record importer counts and
  governance guard changes in the future retirement package.
- For replay, recurrence, provenance, and persistence surfaces, include a
  protected-vs-diagnostic classification before removal.
- For serialization/API compatibility, include a data or caller corpus scan
  before removal.
