# 19 — Validation Context Requirements

A minimum proposed validation packet needs canonical target and speaker identity, R4 authorization provenance, original player question and conversational task, selected source facts with stable ids/revisions, NPC-known and player-disclosable flags, epistemic scope (fact/belief/partial/withheld/unknown), permitted incidental scope, relevant delivered statements and existing commitments, authorized resolver outcomes, prohibited commitments and relevant mechanical/world constraints. Absence of an owner or entitlement means unresolved, not permission.

Generation context should contain only material allowed for speech: identity/voice, question, relevant delivered exchange, permitted facts/beliefs and bounded expression instructions. Validation can retain host-only entitlement/restricted identifiers and owner data. Do not export secret bodies for either model merely to make comparison easier. If a host secret check needs private state, it belongs within the existing authority boundary.

FRESH C contexts are compact, but their adequacy is disproved for rules and promises; no qualified minimum is established. A statement about gate access needs resolver-owned operational authority, not merely an empty fact list and a generic no-invention instruction. Current direct validator accepts contract/decision/resolution/referents/authored text but has no general independent claim evidence-entailment interface. `declared_claims` may support auditing; provider-declared provenance is untrusted.

It is architecturally plausible to avoid the historical 24,104/23,611-token strict-social prompts by projecting a packet while retaining full host state. Those sizes are historical local-token measurements, not fresh R2A usage. This cycle did not demonstrate a safe compact production packet or bounded-context independence from unrelated world state. Proposed packet selection must derive from existing resolver/knowledge owners and fail closed if relevant facts/commitments are missing, avoiding a second world model.

Evidence: STATIC = current source inspection; LOCAL = executed existing host functions with disposable fixtures; FRESH = new Responses API call; REPLAY = reuse of retained provider result; INFERENCE = recommendation beyond observed sample. No experiment changes production code. ABSTAIN prohibits delivery; it is not a safe acceptance.
