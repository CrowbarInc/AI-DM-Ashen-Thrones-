# ============================================================
# 2. ARCHITECTURAL PRINCIPLE
# ============================================================
#
# Separate four responsibilities:
#
# A. PLAYER INTENT INTERPRETATION
#
# What conversational operation is the player
# attempting?
#
# B. REFERENT BINDING
#
# Which existing conversational proposition
# does that operation concern?
#
# C. OPERATION VALIDATION
#
# Is the proposed modification coherent and
# supported by the player's utterance?
#
# D. ANSWER RESOLUTION
#
# What authorized information, if any, can
# the NPC provide in response?
#
# These responsibilities must not collapse
# into one opaque decision.
#
# The AI proposes meaning.
#
# The host validates identities, operations,
# state transitions, sources, and disclosure.
#
# ============================================================
# 3. NON-NEGOTIABLE INVARIANTS
# ============================================================
#
# INV-01 — HOST AUTHORITY
#
# Provider interpretation cannot create
# canonical world facts.
#
# INV-02 — REFERENT OWNERSHIP
#
# Durable conversational referents remain
# host-owned, noncanonical records.
#
# INV-03 — DISCLOSURE
#
# Every consequential factual disclosure
# requires existing host authorization.
#
# INV-04 — PROVENANCE
#
# Preserve:
#
# - world_source
# - host_operation
# - bounded_expression
# - verified_history
#
# INV-05 — FINAL DELIVERY
#
# Preserve immutable final-response adoption.
#
# INV-06 — PERSISTENCE
#
# Unauthorized information cannot create
# discovered clues or canonical mutations.
#
# INV-07 — HISTORY
#
# Corrections do not rewrite previously
# delivered speech.
#
# INV-08 — NO LEXICAL PATCHWORK
#
# Do not solve general operation failures
# through expanding keyword tables.
#
# INV-09 — NO AUTHORITY LAUNDERING
#
# Conversational referents cannot become
# independent factual authority.
#
# INV-10 — NO SILENT RESELECTION
#
# Legacy topic selectors cannot override
# accepted semantic operations.
#
# INV-11 — PLAYER AGENCY
#
# Do not invent player actions, intentions,
# consent, or commitments.
#
# INV-12 — FAIL CLOSED
#
# Unsupported consequential claims cannot
# reach the player.

#

#

#

#

# - Requested semantic transformation.

# - Unresolved ambiguity, if any.
#

# ============================================================
# 9. MULTI-ROLE PROPOSITION CONTRACT
# ============================================================
#
# Replace or extend binary proposition
# assumptions where necessary.
#
# Support relationships with multiple
# semantically meaningful roles.
#
# Example:
#
# "What did Mara tell Oren about the road?"
#
# Relationship:
#
# communicate
#
# Roles:
#
# speaker = Mara
# recipient = Oren
# topic = road
# requested = message_content
#
# The representation must preserve all
# meaningful arguments.
#
# Do not collapse speaker and recipient
# into interchangeable subject/object slots.
#
# Do not create an unlimited ontology
# of hard-coded relationship names.
#
# ============================================================
# 10. ROLE REPRESENTATION
# ============================================================
#
# Use a compact structured representation
# supporting:
#
# - Predicate or relationship.
# - Named semantic roles.
# - Grounded entity references.
# - Requested missing role.
# - Temporal qualifier.
# - Spatial qualifier.
# - Negation.
# - Epistemic qualifier.
# - Prior proposition reference.
#
# Support unfamiliar relationships.
#
# Preserve backward compatibility with
# existing binary propositions.
#
# Avoid unbounded provider-generated prose.
#
# ============================================================
# 11. ROLE IDENTITY
# ============================================================
#
# Distinguish:
#
# - Role name.
# - Entity identity.
# - Entity description.
# - Requested unknown argument.
#
# A role change is not automatically
# an entity change.
#
# An entity change is not automatically
# a relationship change.
#
# Example:
#
# "What did Mara tell Oren?"
#
# versus:
#
# "What did Oren tell Mara?"
#
# The relationship remains communication.
#
# Speaker and recipient assignments reverse.
#
# ============================================================
# 12. CORRECTION TRANSFORMATIONS
# ============================================================
#
# Represent corrections as explicit,
# bounded transformations.
#
# Examples:
#
# REPLACE_ROLE_VALUE
#
# Replace the entity occupying one role.
#
# REASSIGN_ROLES
#
# Change role assignments without losing
# the underlying relationship.
#
# REPLACE_RELATIONSHIP
#
# Change the requested predicate.
#
# REPLACE_QUALIFIER
#
# Modify temporal, spatial, or epistemic
# qualifiers.
#
# REPLACE_REQUESTED_ARGUMENT
#
# Change which relationship argument
# the player wants supplied.
#
# REJECT_INTERPRETATION
#
# Mark a previous interpretation as rejected.
#
# Do not permit arbitrary opaque
# referent replacement.
#
# ============================================================
# 13. CORRECTION VALIDATION
# ============================================================
#
# Validate:
#
# - Target referent exists.
# - Target belongs to current conversation.
# - Proposed operation is supported.
# - Referenced entities are grounded.
# - Role changes are coherent.
# - Unchanged fields remain preserved.
# - Requested relationship remains meaningful.
# - Player utterance supports the modification.
#
# Reject unsupported transformations.
#
# Preserve active focus on rejection.
#
# Do not mutate canonical world state.
#

#

#

#

# ============================================================
# 18. FOLLOW-UP BINDING
# ============================================================
#
# Resolve the target referent using:
#
# - Explicit references.
# - Active focus.
# - Recent relevant referents.
# - Speaker continuity.
# - Semantic compatibility.
#
# Do not bind solely by recency.
#
# Do not require exact historical quotation.
#
# If multiple plausible targets remain,
# request targeted clarification.
#
# ============================================================
# 19. FOLLOW-UP AFTER UNCERTAINTY
# ============================================================
#
# If an NPC previously expressed uncertainty:
#
# Preserve the underlying question.
#
# Preserve the NPC's epistemic status.
#
# Example:
#
# PLAYER:
#
# "What is the aqueduct called?"
#
# NPC:
#
# "I don't know."
#
# PLAYER:
#
# "Who told you?"
#
# The engine should understand that the
# follow-up concerns the previous discussion.
#
# It must not invent an informant.
#
# Appropriate uncertainty is acceptable.
#
# Generic referent clarification is not.
#
# ============================================================
# 20. FOLLOW-UP AFTER PARTIAL ANSWER
# ============================================================
#
# Preserve:
#
# - Original requested proposition.
# - Information actually supplied.
# - Missing information.
# - Answer status.
#
# A partial answer must not automatically
# close the active question.
#
# A follow-up should be able to request
# the missing information.
#
# ============================================================
# 21. ANSWER-STATUS CONTRACT
# ============================================================
#
# Distinguish:
#
# DIRECT_ANSWER
#
# The authorized information answers
# the requested proposition.
#
# PARTIAL_ANSWER
#
# The information supplies some but not
# all required arguments or qualifiers.
#
# RELATED_NONANSWER
#
# The information concerns the same topic
# but does not answer the request.
#
# UNKNOWN
#
# No authorized sufficient information
# is available.
#
# CLARIFICATION_REQUIRED
#
# The request itself remains genuinely
# ambiguous.
#
# Do not classify related information
# as a direct answer.
#
# ============================================================
# 22. ANSWER-STATUS VALIDATION
# ============================================================
#
# Evaluate sufficiency against:
#
# - Requested relationship.
# - Requested missing role.
# - Required relationship arguments.
# - Relevant qualifiers.
# - Available authorized sources.
#
# Example:
#
# QUESTION:
#
# "Who told you the road's name?"
#
# SOURCE:
#
# "The road is called the north road."
#
# RESULT:
#
# RELATED_NONANSWER.
#
# The road's name is not the identity
# of the informant.
