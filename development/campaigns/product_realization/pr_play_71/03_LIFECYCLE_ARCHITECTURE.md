# LIFECYCLE ARCHITECTURE

Frontend static/app.js → POST /api/new_campaign → campaign_reset.apply_new_campaign_hard_reset → fresh session/campaign_run_id and session_id, clean world runtime/combat/transcript → GET /api/state + /api/log after navigation → Start Campaign button → POST /api/start_campaign → _OpeningScope acquires existing runtime lock and captures baseline → opening scene resolver + existing narration pipeline → accepted opening persistence and campaign_started → player-safe projection → reloadAll renders scene, character and actions → /api/action or /api/chat → resolver/world/session owners → file persistence → leave/reload → state/log reads, or /api/snapshots/load → validated snapshot restore → state AND log refresh → continued actions.

Initialization boundary: HTTP start is admitted only for a fresh unstarted session with empty transcript. _OpeningScope holds the existing persistence RLock, rolls back uncommitted opening work, and rejects duplicate starts after commit. Completion requires campaign/session identity, selected scene, persisted opening, visible narration and actions, successful first action and persistence. New Campaign is a silent reset, not the opening turn.

Persistence boundaries: per-action automatic file saves; explicit Save Slots/Create Snapshot captures session/world/combat/character/log. Snapshot restore validates before commit and rolls back failure. Templates and campaign bootstrap are not snapshots. Final reset repair captures the same runtime file bytes before reset and rolls back changed documents on failure. Atomic-write retries only the prepared rename, four attempts over at most 130 ms of sleep; no resolver/provider replay. Multi-process/crash atomicity remains unproven.
