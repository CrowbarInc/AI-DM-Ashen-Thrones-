## Definitions versus instances

Some current IDs survive JSON save/reload unchanged, but this proves field preservation, not uniqueness among copies or ownership transfers. Scene and inventory identity spaces are incompatible. No general transfer implementation guarantees that modified state follows an instance. Unknown JSON fields can survive storage and still disappear from player projection. The current ITEM allowlist in player_http_projection.py:34 is one such downstream boundary.

Keep definitions immutable and optional: a mundane authored shirt need not have an imported template. Importing a dagger definition never creates a dagger in the campaign. Reimport of an existing character must be an explicit reconciliation operation; never overwrite UUIDs/markings based on matching display names or row order.

## Legitimate distinctions and fragmentation

Definitions, instances, attack capabilities, knowledge, ownership rights and read projections are genuinely different concepts. Do not consolidate them into one entity blob. Inventory versus authored fixtures are legitimate specialized hosts. Two mutable representations for one door (controlled entry and physical_state overlay), unqualified legacy IDs, and disconnected inspection/possession references are fragmentation risks. Bind one source to one instance and reject conflicting bindings rather than copy both states into a new registry.

Evidence basis: full game-source term inventory, inspected defaults/importer/models, scene classifier, physical owner, storage, authored consequences, player projection and T04/T06 reports. “No generic owner found” refers to those inspected runtime sources; arbitrary future JSON fields are not executable support.
