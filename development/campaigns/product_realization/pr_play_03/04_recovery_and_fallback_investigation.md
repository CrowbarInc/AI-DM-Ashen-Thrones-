# 04 — Recovery and Fallback Investigation

**Observed:** The historical recovery retains scene_opening identity but evaluates completion under an unrelated generic answer contract. The final sentence is constructed by `immutable_valid_response.safe_nonresolution` → `interaction_completion.generic_ask_completion`, not directly by the empty-output repair helper.

At `_run_resolved_turn_pipeline`, `live_resolution.attach_interaction_obligation` sends the empty internal bootstrap input to `construct_resolution_contract`. Its unmatched-action default is operation=unresolved; the expected-resolution default is answer (`resolution_contract.py:1336,1404`). The separately derived response-type contract still says scene_opening. This is the earliest demonstrated **contract projection mismatch** in the recovery chain. It does not explain the provider's missing envelope.

`live_resolution._select_resolution_mode_body` receives resolution and normalized action (both still carry scene_opening), but has no opening branch or response_type_contract argument. Its final default returns GROUNDED_INFORMATION_REQUEST with `default_existing_resolution`. `attach_interaction_obligation` records that decision, and the narration hub publishes it. The mode is descriptive authority/routing metadata here; it is not, by itself, the function that chooses the final sentence.

`gm._safe_json` returns empty narration for envelope rejection. The hub's general retry machinery sees no selected targeted failure for this controlled empty opening; the original retry count stays zero. `call_gpt` independently refuses any retry-attempt dispatch with ASHEN_DISABLE_PROVIDER_RETRIES. A retry may be eligible in other paths without being sent. The actual path's `retry_exhausted` is set unconditionally by minimal repair; it does not prove a retry happened, or that the six-request admission ceiling was reached (five remained).

The hub's `_repair_terminal_player_facing_if_needed` divides only social/non-social. The non-social call is `ensure_minimal_nonsocial_resolution(gm, session)` with **neither resolution nor response type**. It chooses a local scene-fact anchor, adds nonsocial_empty_resolution_repair and retry_exhausted, and leaves structured_contract_failure metadata intact. Original `hard_validation_attempt_1.text` captures that intermediate anchor line.

`immutable_valid_response.lifecycle_applies` explicitly excludes scene_opening at line 1060. Nevertheless, the hub's later unresolved/no-interlocutor catch-all (`api.py:4260`) invokes `run_preserve_if_valid` without that exclusion or opening response-type requirement. Its `_check` rejects the repaired candidate because structured_contract_failure survives. With no regeneration callback, `_terminal_after_fidelity` ultimately calls safe_nonresolution. Operation=unresolved, no label/interlocutor/question → generic_ask_completion returns the exact historical sentence. The fallback is checked as a fresh text-only candidate, so it no longer carries the envelope-rejection flag and has no opening-specific completeness obligation. `contract_satisfying` is simply hard_valid at validator line 812.

This is the first demonstrated **incorrect recovery acceptance decision**: the generic safe answer is sealed as complete for a scene_opening. The seal records both resolution_kind=scene_opening and expected_resolution=answer. Immutable preservation then prevents the final emission gate from correcting it (`final_emission_gate.py:100`). Fixing text after sealing would violate the delivery boundary and address the symptom too late.

The existing API owner can return an honest opening-failed response without inventing scene content, for example an operation failure explaining that no opening was delivered. It must carry failure status and remain outside successful narration adoption. A better sentence alone does not make an opening successful and cannot correct the start latch or pressure persistence.

Recommended ownership: opening-aware admission/acceptance and failure return in `api.start_campaign` / narration hub, coordinated with its existing persistence tail. Reuse response-type and existing opening validators before adopting immutable success. Do not add a new classifier, fallback subsystem, automatic inference call, or a general change to unrelated NPC answer completion.
