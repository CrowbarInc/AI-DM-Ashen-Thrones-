## 4. Final Chassis Summary

Ashen Thrones' permanent chassis is a forward-flowing runtime architecture.

Player intent enters the runtime transaction spine, owned by `game.api` and related API support. Domain simulation modules resolve mechanics and mutate authoritative state under explicit state authority. CTIR captures resolved-turn meaning after authoritative resolution and before prompt adaptation. Prompt/adaptation packages approved truth, CTIR, visibility, response contracts, and plan context for expression without becoming mechanics authority.

Backend/model infrastructure selects model lanes, invokes the current provider, normalizes backend results/errors, and returns candidate expression. Backend output is not truth. Future providers attach behind a backend adapter boundary and must preserve normalized request/response/error, diagnostics, and provenance separation.

Final Emission owns last-mile legality, sealing, selection, packaging, metadata/FEM, terminal exceptions, and traceability. Validators predicate, repairs remain bounded, sanitizers strip/package/drop illegal artifacts, and fallback remains split by content, selection, application, provenance, and observation.

Persistence stores runtime documents and envelopes; it does not own mechanics, replay policy, or ruleset behavior. Replay, projection, evidence, diagnostics, and telemetry observe finalized runtime surfaces. Provenance records source, family, owner, and lineage; it explains behavior but does not select behavior.

Governance declares doctrine, assigns owners, keeps direct-owner tests aligned, watches drift, refreshes governed artifacts, and manages compatibility evidence. Compatibility residue is not co-equal ownership; it remains active until evidence-backed retirement packages prove safe.

Extension proceeds through owner contracts rather than broad plugin abstractions: domain owners, state authority, action/schema/content validation, CTIR, response policy contracts, model routing/backend adapter paths, ruleset identity/capability paths, persistence envelope, replay/provenance registries, diagnostics tooling, and compatibility workflow.

## 5. Long-Term Architectural Doctrine

Enduring doctrine established by Campaigns 1-6:

1. Preserve one runtime transaction spine.
2. Domain simulation owns game truth.
3. State authority names and guards mutation/read boundaries.
4. CTIR is the resolved-turn meaning surface between domain resolution and prompt adaptation.
5. Prompt/adaptation consumes approved truth; it does not create truth.
6. Backend/model output is candidate expression, not mechanics authority.
7. Extend contracts and owner modules before changing orchestration.
8. Keep Final Emission as last-mile legality, sealing, packaging, metadata, and traceability.
9. Keep validators, repairs, sanitizers, and fallback responsibilities distinct.
10. Keep persistence separate from gameplay semantics and replay policy.
11. Keep replay/projection/evidence downstream of runtime.
12. Keep provenance explanatory, not behavioral.
13. Keep diagnostics observational unless explicitly runtime-packaged by an owner.
14. Keep direct-owner tests as semantic authority before downstream smoke.
15. Preserve compatibility until evidence supports retirement.
16. Treat documentation registries as governance aids unless executable authority exists.
17. Keep internal helpers internal unless a future package proves a real API need.
18. Require concrete product need or repository evidence before reopening architecture.

## 6. Future Development Posture

Future repository evolution should be implementation-first.

Dominant future work categories:

- Gameplay implementation: new mechanics, world systems, non-combat behavior, stateful systems, balancing, and rules refinements through domain owners.
- Content creation: campaigns, scenes, authored data, validation/lint improvements, imports, and content workflows through schema and validation boundaries.
- AI capability: prompt/adaptation improvements, model routing changes, current-provider quality work, and eventual backend adapter/provider implementation if product scope demands it.
- Tools and diagnostics: debugging tools, read-side reports, replay inspection, provenance/lineage reports, stability tooling, and generated evidence.
- UX and product polish: richer local UI, better API projections, player/debug visibility improvements, and operator ergonomics.
- Testing and governance: direct-owner tests, focused smoke, replay/provenance checks, governance refresh, validation coverage, and compatibility evidence.
- Compatibility retirement: evidence-backed removal or stabilization of legacy surfaces through the compatibility register.

These are implementation activities because the chassis already defines where they attach, who owns them, what they must not bypass, and which tests/governance surfaces validate them.

## 7. Remaining Architectural Horizon

Future architectural review is justified only for evidence-backed structural triggers:

- Alternate ruleset architecture: required if alternate ruleset behavior is implemented; must publish identity, version, family, capabilities, domain compatibility, persistence/replay/provenance implications.
- Additional backend architecture: required before adding a second provider or local inference path; must preserve routing/backend separation and keep provider-specific behavior contained.
- Hosted/public API architecture: required if external/public tooling, hosted APIs, multi-user runtime, event streams, or durable external contracts become product goals.
- Multi-user runtime: required if concurrent sessions, identity, tenancy, shared state, or server-hosted play changes runtime ownership or persistence requirements.
- Migration framework: required if long-lived campaigns must migrate across ruleset/backend/schema/persistence versions.
- Player-facing provenance/redaction: required if internal provenance must become player-safe explanation without leaking hidden information.
- Generic plugin architecture: not approved; would require concrete requirements and a future architectural campaign because it would change extension semantics.
- Dependency inversion proposals: required if a change would move mechanics truth into GPT/prompt/Final Emission/replay/governance or make replay/projection drive runtime.

Ordinary feature work is not an architectural trigger.
